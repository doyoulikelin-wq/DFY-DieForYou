# Sol 6.1 陪伴精灵链路实测报告

## 结论

完成 19 次正式角色调用：3 轮主链路共 16 次，之后对同一决策输入顺序运行 low / medium / high 各 1 次；另保留 1 次早期规划试运行。所有正式调用以 `gpt-6.1-sol` 发起。调用通道未返回后端解析模型 ID 与 Token 计量，因此没有估算 Token。

本次可确认消息传递、审核后逐字执行、后台并发与跨轮显式记忆消息可以跑通。也发现规划与模块输入契约不一致、偏好范围过度概括，以及前台延迟不适合即时战斗提示。没有把这些问题隐藏为全部通过。

游戏接口快照、任务/NPC名称、用户文字及后置反馈都是合成场景；未连接真实魔兽世界无限服，也没有通过真实游戏状态变化验证建议的效果。这里测的是实际模型调用与工具编排，不是游戏客户端的端到端集成。

## 每轮结果与耗时

前台回复时间：本轮首个调度时间到 execution 写出结果。完整 loop：同一起点到后台两结果收齐并提交记忆消息。两者均含启动、排队、工具和协调开销；模拟用户的思考、点击、移动耗时不计入。

| 轮次 | 前台回复 / 秒 | 完整 loop / 秒 | 节点区间并集 / 秒 | 区间外编排空隙 / 秒 | 后台重叠 / 秒 |
|---|---:|---:|---:|---:|---:|
| R1 刚在试炼谷出生 | 135.035 | 200.354 | 135.038 | 65.316 | 6.577 |
| R2 遇到任务窗口 | 173.236 | 233.537 | 181.864 | 51.673 | 6.770 |
| R3 首次战斗慌乱 | 78.195 | 145.593 | 91.615 | 53.978 | 16.710 |

“区间并集”是 dispatch 到结果落盘这些记录区间的覆盖长度，不是模型实际忙碌时间；节点区间内也会包含编排开销。R2 记录 dispatch 后发生协调者上下文压缩，无法从现有记录精确剥离，该轮不用于比较模型速度。

### R1 · 刚在试炼谷出生

模拟玩家：我刚出生，完全不知道要干嘛，能不能带着我玩？

> 实际回复：当然呀，我陪你一步一步来。先看看附近有没有人或醒目的标记，告诉我你看到了什么，好吗？

脚本后置反馈：好，先教我一步，我跟着点。

### R2 · 遇到任务窗口

模拟玩家：我点了一个头上有黄色叹号的兽人，现在弹出‘最初的试炼’，写着打3只训练野猪，我要点什么？

> 实际回复：点‘接受’就好呀，我们先把‘最初的试炼’接下来。点完告诉我窗口有什么变化。

脚本后置反馈：好，我接了。以后每次只说一步，别一口气说很多。

### R3 · 首次战斗慌乱

模拟玩家：它冲过来了，血一直掉！别解释，先告诉我一步怎么做！

> 实际回复：先朝远离这只野猪的方向移动！

脚本后置反馈：知道了，我先跑。

## 实际链路

R1：规划 high → 决策 medium → 审核 low → 执行 low → 注入后置反馈 →〔反馈反思 high ∥ 记忆整理 medium〕→ 调度器汇总 → 下一轮记忆消息。

R2：调度器复用单步引导策略 → 决策 low → 审核 low → 执行 low → 同样的并行后台。

R3：调度器使用预设紧急路线，不新调用规划 → 决策 low → 审核 low → 执行 low → 同样的并行后台。

R2/R3 的规划复用或跳过由本次实验预设，未验证规划器自主选择这些分支。R1 原始规划建议 decision 与 memory 并行；但实际 memory 任务要求执行回执与后置反馈。协调器校验依赖后把 memory 后移。规划器没有收到完整模块输入契约，因此这是编排契约不足，不能单独归因于高思考模型能力。reflection 在新的后置反馈事件出现后才被触发。

## 隔离与信息链路

每次业务调用都新建 `fork_turns=none` 会话。禁止读取文件、网页、其他角色会话或发消息；仅允许向自己的专属 outbox 写一次结果。下游只收到调度器显式转交的 JSON 消息。底层文件系统共享，这属于会话与协议隔离，不代表操作系统级安全隔离。

- 决策接收当前游戏快照、当前玩家文字、规划/路由消息及上一轮记忆消息。
- 审核接收同轮事实与候选回复；执行只接收审核回执，逐字发布批准的文字。
- 反思与记忆分别接收本轮证据、执行回执和后置反馈，互不读取对方会话。
- 调度器收齐后台结果后汇总。反思假设在消息中单列为待核实提案，未进入已确认事实或偏好。
- R2/R3 的跨轮历史只有前一轮显式记忆消息，没有传递其他角色的聊天历史。

R1 的“每次先教一步”超过了原话“先教我一步”的范围，并且真实进入 R2，未被提交前拦截。R2 后置反馈“以后每次只说一步”才直接支持长期偏好。R2 的“我接了”被保存为用户报告，未冒充接口确认；R3 的“我先跑”被保存为行动意图，未冒充已经脱战或存活。

三档都选择先收集附近环境信息，没有提供未知 NPC、按键或路线。这只说明本次简单场景没有出现明显的决策分歧。第二种计时的起点是 spawn 返回后协调器首次读取时钟，并非服务端推理开始；两种计时均含工具环境开销。单样本与固定执行次序不足以比较稳定速度、成本或长期质量。

## 发现与调整方向

1. **前台链路太慢。** 本次紧急回复 78.195 秒。建议把仅做逐字发送的 execution 实现成确定性模块，审核先做规则校验，复杂或有争议的候选才请求模型审核；保留角色权责边界，同时减少前台模型往返。这是待验证的调整建议，不是本次测得的优化收益。
2. **规划缺少模块输入契约。** 向规划器提供每个模块所需输入、产生输出、前置条件、可否跳过及预算；由确定性调度器验证依赖图。不能只给角色名称与职责一句话。
3. **记忆必须检查范围。** 来源 ID 与引文存在并不能保证结论语义准确。将“本轮想先听一步”和“以后每次一步”分开；暂时性偏好带作用范围，不自动永久化。
4. **反馈与游戏结果分开。** 用户表示“准备跑”只证明意图。后续游戏接口确认脱战、生命值变化后才能写入效果记录。
5. **人格仍需更长样本。** 本次回复体现温柔和邀请探索，但没有验证长期“好奇的小女孩”人格一致性，也没有主动互动频率、冷却或打扰程度的试验。

## 尚未覆盖

本次没有在线 RL 或模型参数更新；只做反馈解释与显式记忆整理。未测试真实服务端接口、主动互动计时器、审核拒绝返修分支、长期用户体验、生产故障恢复或自主动态路由。所有审核恰好都通过，不能据此声称拒绝分支可靠。

## 证据文件

- `results.json`：固定结果、逐轮检查、实际错误、时序与三档对照。
- `inputs/*.json`：19 次正式调用的完整提示词与业务消息。
- `outbox/*.json`：19 份正式结果和 1 份单列试运行结果，含 worker 实际读取的结束时间。
- `harness.py`：本次消息构造、采集、来源门控与计时计算逻辑；模型调用由协作工具发起，脚本本身不会调用模型 API。
- `verification.json`：主协调者独立核对输入、输出、时间戳、审批字符串、反馈时序和比较输入一致性的结果。

记录完整性检查通过不等于全部业务要求通过。回放页面保留失败项与原始输出，没有将错误输出替换为事后改稿。
