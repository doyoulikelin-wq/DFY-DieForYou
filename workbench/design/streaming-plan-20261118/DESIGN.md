# 大肥鱼：尽快交付有用内容的 Streaming 路径

资料核对：2026-11-18，Asia/Shanghai。此文和交互页是工程设计、预算与验收路线，不是已完成的 API 性能测试。

## 1. 现状与目标

过去 8 个基础场景的“派发 → 候选审核完成”中位数为 21.324 秒。它包含会话启动、排队、工具和编排，不能当作 API 的 TTFT。两个复杂完整 loop 分别为 263.249 秒、274.828 秒，存在编排空档。此前实际日志没有逐 token 流、API usage 或客户端渲染时间。证据见[真实回放](https://companion-agent-studio-nov15.mylssssdddd.chatgpt.site/natural-test.html)。

新 FAQ 资产包含 958 张情境卡、1,851 个回答变体、12,382 条问法索引记录。160 次本地热内存检索中位数 0.481 ms、P95 0.706 ms；59/59 门控夹具通过。这只说明局部代码的表现，不代表自然语言命中准确率、真实客户端端到端速度或人设质量。卡片中仍有待实现的适配条件，必须逐批批准，不能全量自动上线。

本轮主目标：缩短 **从玩家输入到第一段独立有用内容实际显示** 的时间。空泛开场不计；进度与澄清可以有用，但要另标任务尚未解决。

## 2. 主要难点

- 简单问题也承担模型调用和多角色接力的等待。
- Planner 在没有可获得的新信息时仍继续运行，产物没有新增价值。
- FAQ 相似命中不能证明当前意图、角色、规则集、游戏状态和偏好都适用。
- 生成期间游戏状态会变，后台记忆提案也可能晚于新明确偏好。
- 逐字流并不证明事实正确，已显示的句子不能撤回为未发生。
- 扩充问法数量不会自动改善大肥鱼的自然感；必须控制主动性、重复、语气与沉默时机。

## 3. 调研后的选型

| 方法 | 能解决什么 | 本项目用法与限制 |
|---|---|---|
| [Redis 整答语义缓存](https://redis.io/docs/latest/develop/use-cases/semantic-cache/) | 合格命中可以直接复用完整答案 | 先使用现有本地索引与硬条件，暂不为技术名词引入在线 embedding；状态校验不能省 |
| [Anthropic 条件路由与动态编排](https://www.anthropic.com/research/building-effective-agents) | 根据任务选择路径，独立工作可并发 | 角色职责保留，调用按需；Planner 要有具体未完成产物与可获得证据 |
| [OpenAI Streaming](https://developers.openai.com/api/docs/guides/streaming-responses) | 生成未完成时即可逐步传输内容 | 首 delta 进入内部缓冲，完整语义段审核后发布；记录客户端真实显示 |
| [OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) | 复用稳定前缀的处理结果 | 每个 Agent 保持自己的公开指令前缀，当前状态放后；缓存命中仍需生成新输出 |
| [Fast](https://developers.openai.com/api/docs/guides/fast-mode) / [Ultrafast](https://developers.openai.com/api/docs/guides/ultrafast-mode) | 同模型的服务速度选择 | 在同题、同输出长度和同质量门槛下测真实差异；价格更高，不能预设收益倍率 |
| [Skill Training](https://skilltraining-project.github.io/) | 离线更新外部技能文本 | 将方法迁移为情境重建、比较、修订与留出集；原论文任务是短剧写作，不能据此承诺本项目效果 |
| [vLLM APC](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/) / [推测解码](https://docs.vllm.ai/en/latest/features/speculative_decoding/) | 自托管模型的 prefill / decode 优化 | 后续自托管候选；不是客户端可以替当前托管 API 打开的通用开关 |

各方法在本项目的采用方式属于设计推断。供应商宣传的速度与论文结果没有搬用成本项目的实测数字。

## 4. 在线执行路径

### A. 确定性直答

输入包 → 本地检索/路由 → 已批准完整表达 → 发布审核 → 玩家显示。

必要前提：可信接口或明确用户文字确认当前意图与触发条件；规则集、知识版本、证据槽位、相关状态版本与偏好均有效。整个路径不调用在线 embedding 或模型改写。已知短答直接整句显示，不人为增加打字机等待。

建议首批只批准约 100 张高频卡。所有未实现的自然语言条件视为未通过，不因检索分数高而放行。

### B. 单次快速决策与表达

检索未合格命中 → 一次 `gpt-6.1-sol` low → 语义段缓冲与审核 → 玩家显示。

一次调用同时处理普通意图判断与短回答，不额外串一个路由模型、润色模型、全量审核模型。输入只包含本轮必要证据与少量相关知识。涉及无法验证的新游戏事实时，该段暂停、澄清或升级，不让规则自称证明任意自由文本。

当前官方[模型文档](https://developers.openai.com/api/docs/models/gpt-6.1-sol)列出 low、medium、high、xhigh、max；本设计延续用户指定的 Sol 6.1，不假设支持 none。服务档位对照也不更换模型。

### C. 有收益的复杂规划

路由先判断有没有独立可靠的第一步。有则沿直答路径先交付；没有则不能虚构快速首步。

Planner 生成 DAG：所需角色/工具、依赖、允许并发组、截止时间、取消条件和预期产物。工具结果合流后，由快速决策生成新增结果。该复杂决策单次输入预算为 1,200–2,400、非推理输出 80–180；与普通短答预算分开。独立读取并发，缺上游结果的步骤等待。若没有新信息、第一答已经解决请求，跳过 Planner 或禁止补充。

交互页的半小时例采用合成任务 A/B/C，不是游戏真实任务攻略。Planner 先确认需读取任务状态与路线估计，两项只读任务并发，决策等待两者完成。C 的耗时仍未知，成果明确标为已知信息下的保守安排，未证明全局最省路。

### D. 状态失效与静默

相关状态版本、reply epoch 或偏好变化时，在发布门丢弃旧候选；尽力取消旧模型，但取消未确认不等于推理停止，也不等于零费用。依赖未变化的无关字段无需让所有输出一律失效。

用户明确说“不用回复”时，偏好立即生效并提交 silence；不追加“好的”。这类成功不计为第一有用句 0 ms，而记为“不适用”，另统计偏好生效时间。

## 5. 时间和 token 预算

下列是拟定工程目标，不是测量结果、服务 SLA 或模型性能预测。实际网络、负载、缓存冷启动、隐藏推理及任务难度可能超出。

| 路径 | 第一有用交付目标 | 前台回复完成 | 模型调用 | Token 规划口径 |
|---|---|---|---:|---|
| 合格 FAQ / 确定事件 | 50–200 ms | 同时完成短答 | 0 | 在线模型 token 为 0，离线成本另计 |
| 单次 Sol low | 1–2.5 s | 2–5 s | 1 | 输入 1,200–2,200；非推理输出 30–100；隐藏 R 待测 |
| 复杂规划，有合格首步 | 首步 50–200 ms | 3–8 s | 示例 2 | 输入合计 3,000–5,900；非推理输出 280–680；R₁+R₂ 待测 |
| 可选后台反思 + 整理 | 不阻塞前台 | 后台预算 10–60 s | 0–2 | 入选例输入 1,800–3,600；文本 180–370；隐藏 R 待测 |

模型配置初设：快速调用生成上限 1,024；Planner 4,096；high 反思 8,192；可选 low 整理 2,048。这些是请求预算上限，不是期望消费量。`max_output_tokens` 包含可见文本与隐藏推理；上限过低可能导致 `incomplete`，不可把残缺结果计为成功。[OpenAI 延迟优化文档](https://developers.openai.com/api/docs/guides/latency-optimization)

账目口径：预算中 I 是输入，O 是非隐藏推理的生成文本（包括 JSON / 工具参数），R 是隐藏推理。合计 I + O + R。实测 `usage.output_tokens` 已包含 R，不能再加一遍；应保留 provider 原始 usage。cached input 是输入的子集，单列命中和费用，不从输入量中“消失”。

平均每轮成本还要计入抽样反思、记忆触发、预取、重试和已取消请求。前台得到 0-token 直答不意味着整个产品没有离线或后台成本。

## 6. 流式日志契约

每轮至少记录以下事件：

1. `input.received`、`state.packet_created`、`route.selected`
2. `model.request_sent`、首个非空 `response.output_text.delta`
3. `candidate.chunk_ready`、`gate.accepted / rejected`
4. `delivery.sent`、`client.first_paint`、`client.first_useful`
5. `response.completed / failed / incomplete`、`client.final_paint`
6. `reflection.proposed`、`memory.cas_committed / rejected`

建议字段：trace_id、span_id、agent_id、turn_id、reply_epoch、dependency_versions、preference_epoch、source_ids、card_id、model_requested、model_returned、effort、service_tier_returned、原始 usage、error_code、cancel_status、token_budget、deadline、quality_result。

前台回复完成统一取最后一段实际显示，不等 API 流结束；novel 例为 2.3 s、复杂例为 5.5 s、旧状态例为 1.05 s。另记 task_status，区分完全解决、保守方案、澄清和进度。

API TTFT 使用服务端同一单调时钟，从请求发出到第一个非空文字 delta。客户端等待使用客户端同一单调时钟，从输入提交到实际渲染。跨机器时钟不能直接相减；用 trace/span 关联各段，墙钟只用于阅读。首 `response.created` 不等于首文字，SSE event 数不等于 token 数。

## 7. Agent 隔离与后台调度

每个 Agent 独立上下文和工具权限。其他 Agent 不能查询其私有记忆，只能收到显式 OutcomePacket、PlanPacket、ToolResultPacket 或获准的 MemoryExcerptPacket。不共享 conversation ID / previous_response_id。公开人设规则可以作为显式输入复制；KV 缓存属于计算复用，不改变信息授权。

明确用户偏好即时通过规则应用。后台只提案，提交时比较 expected_memory_version 与最新 preference_epoch，拒绝旧提案覆盖新明确输入。复杂但低价值的反思可以抽样，初始建议 5%，重要纠正按事件入队；这是待验证的调度参数。

前台保留队列和并发额度，后台不占满资源。优先级为：当前用户提问、必要状态更新、用户请求的补充、主动互动、反思整理。整体是事件驱动，不用人工工具轮询作为产品调度器。

## 8. 自然感与主动互动

优先调整表达的适用时机、内容长度与完整变体；不把“重新调用一个模型润色”放回每次命中的关键路径。普通小怪不欢呼；首领/重要敌人胜利需要击败与参与证据，并服从当前安全与安静偏好。故事分段且尊重剧透范围。

现实世界只来自玩家文字。大肥鱼可以说“我只能借你说的话想象窗外”，不能声称看到房间、听到雨或知道玩家状态。她的天真是珍惜玩家分享，不催问、不内疚绑架。

主动问题初设 5–10 分钟冷却，前一问题没得到回应时不追加催问；战斗、明确安静、没有互动预算时不发。时间参数是产品假设，须用实际用户体验修订。

## 9. 全流程验收与调整

先完成真实 API / 客户端埋点，再逐项改变架构。主要路径至少 200 例建立探索基线，稳定后每组扩至 1,000 例以上；冷/热缓存、服务档位、并发、网络分层统计 P50/P95、失败率和任务质量。不能由六个设计场景计算生产分位数。

高频卡先做约 600 个留出情境，隔离近似问法，包含同问异态和不同版本。区分召回率、通过门控比例、合格直答率和错误直答率，报告置信区间。候选错误时收紧条件；检索漏召回才扩展别名。大量同模板问法不能充作独立样本。

首有用交付的探索验收线：直答 P95 ≤250 ms，普通模型 P95 ≤3 s；普通完整短答 ≤6 s，复杂完整结果 ≤8 s 目标另报达成率。需要更多证据的难例允许慢，必须诚实标记任务未完成。

竞态集要求旧状态/旧偏好可见交付为 0；故障集覆盖断流、超时、incomplete、重复、乱序与取消未确认。若无法满足，停止扩大直答范围并修门控。

自然度用至少 100 组配对样例盲评，分别检查有用、可信、体贴、不打扰、不过度可爱。Skill/FAQ 更新先经过离线评审与留出集，形成可回滚版本后批准，不自动改变已上线的人物设定。

## 10. 本轮交付与未实现事项

已制作：四章节交互页面、十个可点击模块、六种预算时序、三泳道播放、玩家聊天窗口、逐事件 JSON、源链接、预算与验收表、可下载 HTML/JSON/说明文档。原实测仍在原日志页，未被模拟事件覆盖。

尚未完成：真实模型 API 速度实验、真实游戏适配器联调、运行时语义审核、生产任务调度器、自然流量命中率和真实玩家盲评。本轮验证页面本身，不将展示实现声称为陪伴后端已经上线。
