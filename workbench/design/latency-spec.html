陪伴精灵：快速交付与自然互动设计

版本：2026-11-17。性质：待实现与验证的技术设计。本页演示不调用模型、不连接游戏。延迟和 Token 范围均为起始目标或软预算，历史实测单独列出。所有业务模型先统一使用 gpt-6.1-sol 的不同思考强度，便于比较架构；不默认引入其他小模型。

运行时信息边界：本版只接收魔兽内部接口、用户文字，以及从这两类来源明确保存的历史记录与已验证技能。文中的检索是在这些材料内取证，不默认加入网页、视觉、麦克风或其他数据源。模型已有通用知识可帮助提出核实方向，但不能当成当前无限服的实时事实。本文引用的官方文档用于工程设计，不是精灵在游戏中的额外感知。

一、从参考流程到可运行设计

保留“简单问题快处理、需要信息先查询、复杂问题多思考、学习放后台”的主线。增加四个必要约束：本地路由不先等待模型；当前状态和明确偏好同步生效；只在依赖满足后交付相关结论；每条发言在发送时重新检查是否仍适用。

产品的第一目标是用户尽早得到当前可用的一步。界面有反应、开始出现文字、出现有效建议、完整任务完成是四个不同指标。“好问题”“让我看看”只能算接收或进度，不能算有效交付。完整建议来不及时，有依据的局部回答、关键澄清或真实进度分别计量，不能互相冒充。

“多 Agent”首先是职责和权限的分工，不等于每轮必须启动多个进程、传完整历史、串行调用全部模型。正常链路以 0 次或 1 次模型调用为优先；确有依赖时允许增加，并记录原因和实际请求次数。

三、四类请求，按需要选择路径

路径适用条件执行顺序模型调用
A · 已验证技能明确意图、已验证动作、所需状态齐全、条件仍成立。条件检查→选合适的短表达→发送检查→展示。0；本地代码。
B · 单次快速回答普通交流、说明、已有证据能够回答的小问题。最小消息包→Sol low 同时判断内容和生成角色表达→按语义段检查→展示。通常 1；不再追加通用润色。
C · 需要新证据当前接口字段缺失、知识版本需核对、任务内容尚未读取。并行读取独立资料→只保留相关结果→Sol low／medium 回答。检索由规则可确定时通常 1；若需模型决定并调用工具，续接会增加推理轮次，必须如实计数。
D · 复杂任务跨目标权衡、未知任务结构、多个相互依赖步骤、前一路径无法可靠完成。复用已有流程或按需规划→并行取证→依赖就绪后 medium／high 推理→必要语义审核→交付。按图执行；首版给每轮 3 次前台请求软上限，超过后明确降级、分段或等待用户的新信息。

本地路由先检查“停止／静音／纠正”、明确游戏事件和可证明的技能条件。无法确定的自然语言交给本次快速回答处理，不额外创建一个“分类模型→回答模型”的固定链。复杂度不能只看句子长短，也不能把模型自报的置信度当可靠性证明；路由阈值需要用有标注的任务集校准。

用户问话优先于普通游戏提示；新的关键状态变化可以打断过时的建议。战斗中的主动提示只发送条件严格满足的短提醒；同类提醒合并。用户明确要求停止主动说话时，主动队列全部服从设置，不擅自把某类提醒重新打开。

以下是输入与可见输出的起始预算。输入预算包含完整固定前缀与动态内容；命中缓存的前缀仍属于 input_tokens，cached_tokens 是其中一部分，不能按零输入处理。推理 Token 单独观察，但已经计入 API 的 output_tokens，不能重复相加。表中可见输出范围不是 API 总输出，也不是 max_output_tokens 的直接取值；该参数同时限制推理与可见输出，过低会造成回答不完整。全部数值是软预算，未实测。

角色／模块职责与边界配置建议输入／可见输出是否阻塞首句
协调器与路由持有自己的短期状态，更新偏好，选择已有流程，发不可变消息包；不把自身状态变成各角色可随意查询的共享记忆。常驻代码0 模型 Token只做必要的本地工作。
快速决策／表达已有信息下给最小有用回答、必要澄清或请求升级；不能伪造接口结果和执行成功。Sol low稳定内容约 1.2–2.4k，动态 150–600；输出 40–140 tokens。足够短的提示词不为缓存强行补长。普通请求的唯一主模型调用。
规划 Agent生成有依赖、权限、截止时间和结束条件的任务图；不能删除发送检查、扩张工具权限或无限自我调用。Sol medium；必要时 high2–5k／300–900只有新复杂任务需要；常见流程由代码复用。

审核确定性规则检查来源、权限、依赖版本、失效条件。自由文本的语义支持不能只靠规则判定；高影响或新型建议按需加语义审核。规则；按需 Sol low／medium规则 0；模型约 1–2.5k／80–200必须的检查在发送前；不相关审核不阻塞。
执行／统一交付唯一的发送出口；拥有发言锁、去重、截断、客户端消息状态；本阶段仅给建议，不操作游戏。代码0检查当前语义段后发送，不等完整后台报告。
反馈反思从失败、纠正和实际结果产生改进候选；不能直接改人格、提示词、技能或长期偏好。Sol high3–8k／300–800后台，失败事件或空闲批次触发。
记忆整理管理自己的记录，区分明确偏好与推测，合并／过期／撤销；按要求发送摘要，不给其他角色开放共享检索权限。明确指令代码处理；整理 Sol low／medium0.8–2.5k／100–300长期整理异步；用户当前明确约束立即生效。

角色可以有独立会话与存储，但运行在常驻服务内，不需要每条消息重新启动工具进程。前台资源与后台队列分开：首版每用户最多 2 个活跃前台模型请求，后台最多 1 个低优先级任务；全局并发受实际账户配额约束。上述上限是待压测的初始值。

五、规划 Agent 怎样规划其余 Agent

保存四个已验证流程模板：技能直达、单次回应、查证后回应、复杂多步。规划器在后台提出模板调整；运行时由代码判断适用条件。新复杂目标才临时规划。规划结果至少包含节点角色、输入来源、依赖、可用工具、超时、最大调用数、失败出口和成功条件。

  "plan_id": "example-plan-18",
  "reply_epoch": 18,
  "expires_when": ["goal_changed", "combat_started"],
  "nodes": [
    {"id":"quest", "kind":"read_quest", "needs":[]},
    {"id":"capabilities", "kind":"read_capabilities", "needs":[]},
    {"id":"reason", "role":"decision", "effort":"medium",
     "needs":["quest", "capabilities"]},
    {"id":"deliver", "kind":"delivery_gate", "needs":["reason"]}
  ],
  "max_model_requests": 3,
  "max_foreground_concurrency": 2,
  "fallback": "ask_one_missing_question"
}

示例中两项读取并行，推理等待二者，交付等待相关检查。规划本身若发生，算入请求预算。编排器先验证无环、角色与工具白名单、所有必要依赖和预算；不合法的图使用已有流程或询问缺失信息。

同一请求可以并行准备第一条可靠建议和复杂方案，但只在第一条建议不依赖未知结论时启用。快速分支和深度分支各自收到显式信息包。若深度结论必须继承第一句的承诺，证据读取可以并行，最终深度生成则等待第一句提交，并收到“已交付事实／承诺”消息。已经在执行的独立调用不会自动获得后来的发言。

若两条生成确实同时开始，深度结果先作为候选；提交前与已发送内容核对。结构化动作可用规则去重，任意自由文本的语义冲突需要校验；必要时发新的显式消息进行续接、重新生成或语义审核，增加的请求计入预算。预算不足时延后或放弃补充，不假定另一个 Agent 已经知道新信息。代码拥有唯一发言权，后台 Agent 不能直接推送给玩家。

深度结论晚到时先判断：目标仍在、内容有新增价值、状态仍适用、用户没有换话题。条件不成立则丢弃或仅留内部记录。后台算完不等于用户需要再听一遍。

六、信息隔离、状态新鲜度与中断

各 Agent 无共享可修改对象、共享聊天历史、通用记忆库或跨角色会话续接。协调器拥有自己的事件账本，给角色发送最小必要副本。相同事实可以分别被发给两个角色，这属于明确传信。日志用于审计，不能成为角色偷偷读取其他角色历史的入口。

  "reply_epoch": 18,

  "user_text": "先别讲那么多，就说下一步",
  "state_dependency_versions": {"quest": 8, "combat": 12},

  "unknowns": ["custom_server_reward_changes"],

消息中的未知项应明确保留；没有字段不代表值为零或不存在。保留最近 2–4 轮中相关的原文、尚未回答的问题和已做承诺；涉及更早事件时通过显式检索消息补充，不能只给压缩摘要而丢失“这个／刚才那个”的指代。使用差量消息时，接收者必须已确认相同基线版本；新会话应收到完整的最小快照，不能假定它“记得上一轮”。任务文本和检索材料标为外部数据，不能修改角色权限或系统规则。

同步处理：当前用户原文、指代对象、明确纠正、当前交互偏好、最新相关游戏状态、已经发送的内容、取消标记。异步处理：长期摘要、经历归档、风格偏好归纳、失败反思、技能改进。用户说“这次只说一步”只影响本轮；“以后每次只说一步”才提出长期偏好。“别啰嗦”先约束当前会话，不擅自推断为永久人格设定。

结果带读到的依赖版本。检查具体依赖，例如任务对话、目标、战斗状态、技能可用性，而不是任何生命值变化都让全部任务失效。字段有效期按风险配置并根据真实接口刷新率验证：战斗字段可从 100–300ms 的新鲜度目标开始评估，任务界面按事件失效，版本知识按服务器能力与版本区分。接口达不到目标时，不发布需要更高新鲜度的实时指令。

用户改目标／停止、相关状态改变时，增加对应回复版本，停止尚未发送的段落，尝试取消 API；取消失败的迟到结果仍不得出声。客户端也检查版本，避免网络缓冲把旧消息送达。已经显示或播放的内容无法撤回为“没说过”，必要时给明确更正。语音扩展阶段必须另外清空 TTS 与播放缓冲。

记忆补丁采用提交前版本比较；冲突则重算或丢弃，绝不覆盖更新的明确指令。游戏 API 与用户陈述冲突时分别保存来源与时间，重新核对，不能悄悄把其中一方改成确定事实。

七、快速表达怎样保留自然感

固定的是好奇、坦诚、尊重玩家自主选择；变化的是句子长度、主动程度、语气和当前关注点。好奇不要求每句提问，活泼不要求玩家受挫时继续兴奋。没有视觉或声音输入时，不声称看见画面、听到语气或知道真实情绪。

当前场景表达策略不应该发生
用户问下一步先给一项可执行建议。缺关键字段时只问一个能改变建议的问题。重复询问接口已经返回的数据。
进入战斗已验证条件下短句提醒，无闲聊、无解释长段。继续播报刚才的任务规划。
明确受挫或纠正承认具体问题，更新当前信息，修正下一步。固定“你真棒”、无依据情绪诊断、长篇自责。
平静探索允许一句与已知事件有关的感想或有价值的问题。每条末尾拼“呀／嘿嘿／好吗”。
用户要求简短下一句立即缩短，默认停止追加解释和主动追问。等后台记忆写完才改变。
已经回答，暂无新信息安静，等待新事件或用户。为活跃度强行继续发言。

把“当前沟通目的＋证据＋篇幅＋允许提问与否＋最近说过的开场”放进同一次生成。不要额外追加润色 Agent。已验证技能可以保存少量审核过的表达版本，按场景和最近重复选择；不随机添加事实、不机械轮换句尾、不为了拟人增加等待。

最终交付者是代码出口；语气由当前负责生成的角色在同一请求内完成。只有确实需要合并多个不同结论时，才考虑一次额外整合，并把开销记入链路。

八、边说边想：按可交付内容分段

第一层是客户端立即显示“已收到”状态或精灵朝向变化，目标是让用户知道输入生效。第二层是首个可靠的有效内容。第三层是新的证据允许时的补充。客户端反馈不能冒充模型已经理解或已经完成查询。

输出按完整语义段提交：不要把“现在可以……”先播出，然后才发现后半句是“……但你仍在战斗，先等等”。自由文本保留一个短句的检查缓冲；严格的技能模板可快速直出。速度与审核需要一起测，不能为了 TTFT 数字越过必要检查。

语义段协议是应用层设计，不是声称 API 原生提供这些业务字段：

{
  "turn_id":"example-turn-42", "reply_epoch":18, "segment_id":1,
  "kind":"answer", "text":"先接下这个任务。",
  "evidence_refs":["game.quest.dialog.8"],
  "valid_while":["can_accept", "not_in_combat"],
  "supersedes":null
}

可选实现是逐条短记录流、或短句缓冲后附证据绑定；必须验证格式和支持关系。结构字段只证明“引用了哪个来源”，不能自动证明自然语言被该来源蕴含。复杂或高影响建议需要语义校验，无法核实则澄清或收窄。不要让完整长 JSON 的解析阻塞所有前台文字。

“我查一下”仅在真实读取已发起且预计需要等待时出现，每轮最多一次；已经拿到结果时直接回答。“好问题”一类自然接话可以偶尔出现，但要符合当前交流，不能成为每轮必播的口头禅，也不计为有效建议。不确定结果没有可靠局部结论时，使用关键澄清或真实状态显示，不编一个建议来冲速度指标。补充默认最多一次；状态变化或用户请求详解可以开启新段。

九、缓存、Skill 和推测准备

机制存什么失效与边界
KV／Prompt 缓存相同提示前缀的模型计算状态。由服务商管理；命中不免除新的推理和生成。相同模型与相关配置、稳定前缀；角色上下文保持独立。
知识缓存带服务器／版本／来源／有效期的解释材料。版本或能力变化即重新核对；不把其他服攻略当当前事实。
已验证 Skill触发条件、所需字段、动作意图、短表达范围、失效条件、已覆盖测试。缺字段、状态不符、未知收益或有代价选择时退出直达路径。
答复缓存少数稳定 FAQ 或短技能表达。检索相似只产生候选；还要核对意图、状态、版本、偏好、最近重复。不能直接重放带旧血量、旧 NPC 或旧目标的整段话。

以“接受任务”为例：只在用户有接任务意图、当前对话确实可接受、没有奖励选择／花费／未知副作用、游戏接口能证实前提时直接建议。未知无限服行为不套用普通服假设。本设计只给建议，不替玩家点击。

Sol 的缓存采用稳定角色规则／工具定义在前、当前状态和用户消息在后；用真实 cached_tokens 判断效果。满足最低前缀要求时可在角色加载阶段预热，不把预热放到用户刚提问之后。不要为了追求命中率堆叠全部技能和完整历史。分别测试更短输入、缓存复用、预热的首有效回复与成本。

网络层先复用 API 客户端和连接，使用 HTTP 流式作为容易测量的基线。多步工具流程再比较 WebSocket；它与 KV 缓存是不同优化。标准、Fast／Ultrafast 按实际可用性做同题比较，不能拿不同任务的响应速度当服务档位收益。

基于可观察的近期事件，可以在后台预取下一步可能需要的只读信息，例如任务内容。准备结果带依赖版本，真正使用时再核验。不预执行游戏操作；不每秒重规划；预取命中率、浪费和是否挤占前台资源都要记录。

十、主动试探和后台学习

主动互动同时要求：出现新信息、与当前目标相关、时机合适、用户没有禁止、没有正在等待回答的问题。起始策略：平静状态主动试探最多每 8 分钟一次，并限制 30 分钟内最多 2 次；这是上限，不是定时任务。一次未回应不追问，明确拒绝后本场停止试探。“别主动说话”持续生效到用户改变。用户主动提问不受主动冷却影响。

探索的对象是帮助方式，例如先讲一步还是解释原因；不能只为增加停留时长诱导连续聊天。使用显式选择、纠正、真实任务进展和打扰反馈评价效果。“没有回复”不能直接推断为讨厌；失败后情绪也不能当作模型指令有问题的唯一证据。

后台反思由新型失败、用户纠正、工具异常或空闲批次触发；日志立即写入，重反思可以排队。记忆按来源与范围合并。反思产生的提示词、路由与技能更新先进入候选版本，经过固定回归集和保留集检查，再以小流量试用并保留回滚。不要让每一轮自我评价立刻修改线上人格。

SkillTraining 一类技能文本优化可以作为后续离线改进候选，但本版提速不依赖训练成功，也不将它描述为已经实现模型权重在线强化学习。优化目标先满足正确性与打扰边界，再比较首有效内容时间、自然度和成本。

十一、WoW 场景示例：均为设计演示

可用输入拟议回复／行为关键原因
兽人萨满 1 级；任务列表为空；没有附近 NPC 数据；用户“我不知道该做什么”。“我们先找个任务。看看附近有没有能交谈的人，点开后我帮你看。”给一步，不编造 NPC 名称、位置、黄色标记；让用户提供接口缺失的信息。
用户想接任务；接口明确对话可接受；技能全部条件通过。“先接下这个任务。”零模型路径可处理；不额外加一句好问题或固定夸奖。
明确反馈“别啰嗦，每次一步”；当前偏好同步更新。“好，每次一步。”；后续回复立刻遵守。当前会话立即生效；是否永久保存依原话范围判断。
接口证明正在战斗、法力为 0、所用技能需要法力；用户问为什么放不出技能。“蓝用完了，先别反复按这个技能。”只解释已确认原因；不把这条提醒当成解决整场战斗。
旧任务建议尚未发送，当前已进入战斗。丢弃旧建议，按新请求和新状态决定是否提醒。不会突然插入“去找人交任务”。
玩家要求复杂升级路线，但该无限服经验倍率、任务奖励未知。“先把你正在做的任务处理完；后面的路线还缺这个服的经验倍率。”仅在当前任务可继续且用户目标允许时使用，否则直接问倍率。可靠部分与未知部分分开；不声称已经算出最优路线。
平静时用户主动问地名；接口明确当前位置是试炼谷。“这里叫试炼谷。刚出生就要试炼，名字还挺认真。”好奇来自当前已知事实；无需每句问用户问题。

如果用户纠正任务数量，先登记冲突并刷新可用接口；若接口不支持刷新，就明确缺失。禁止虚构“我刚看见了”“我帮你操作好了”或用户未表达的情绪。

十二、计时、日志与失败定义

客户端以同一个单调时钟记录：点击发送、接收反馈、首个可见文本、首个有效建议、最后一段展示、用户打断与本地停止。服务端分别记录排队、路由、取证、API 请求、首文本事件、语义段检查与发送；用 trace 关联，不直接相减两台机器未经同步的时钟。

指标定义与起始目标
接收反馈用户发送→客户端确认接收；p95 ≤150ms。只表示 UI 反馈，不表示模型理解。
技能首有效建议用户输入／事件→玩家看到适用建议；p95 ≤300ms，包含真实接口与客户端。
单次模型首有效建议初始挑战目标 p50 ≤1.5s、p95 ≤3s；需要直连实测，未保证能达到。
复杂任务可靠首个局部交付单列；完整答案按任务分组报告，不能以固定 3 秒要求代替正确性。
打断用户停止→本地不再展示／播放旧内容；p95 ≤150ms 为初始目标。服务端取消与节省 Token 另计。
完整 loop前台交付完成、后台正常任务完成分别报告；取消／过期／延后任务保留状态，不能混入前台等待。

每次真实 API 请求记录 requested_model、returned_model、effort、service_tier、prompt_version、skill_version、input_tokens、cached_tokens、cache_write_tokens、output_tokens、reasoning_tokens、latency、cancel_status。cached_tokens 与 cache_write_tokens 属于输入计量的分类，reasoning_tokens 属于 output_tokens 的组成，计算总量时不要再次相加。未知计量使用 null，不能填 0；模型角色调用数与实际 API 请求数分开。预热、重试、取消和预取的费用同样计入。

业务日志记录 turn_id、route、route_reason、消息发送者／接收者、依赖版本、证据引用、语义段、是否展示、丢弃原因和用户反馈。保存业务摘要和可审计依据，不收集或展示模型私有思维链。

建议错误码：STALE_DEPENDENCY（证据变了）、PREFERENCE_CONFLICT（偏好更新）、MISSING_EVIDENCE（信息不足）、UNSUPPORTED_CLAIM（结论缺支持）、DUPLICATE_SPEECH（重复出声）、ROUTE_MISS（路径错误）、MODEL_TIMEOUT（超时）、INCOMPLETE_OUTPUT（预算截断）、STALE_MEMORY_PATCH（旧补丁）、UNWANTED_PROBE（不合时宜的试探）。真实发生记录和故障注入演示分开。

自然度不能只用词语多样性衡量。盲评多轮对话的贴合场景、性格连贯、简洁、帮助程度与打扰感；统计重复开场、无必要追问、用户纠正／打断／静音，以及明确偏好是否在下一句生效。闲聊、引导、战斗和复杂规划分别评价。

十三、验证与上线顺序

  1. 先建立直连基线。恢复旧三轮场景，新增自由聊天、未知服务器规则、纠正和中断用例；常驻服务直连 Sol low，加入客户端时间和 usage。先用小样本排除埋点错误，再对每类积累至少约 100 次代表性请求，明确小样本 p95 的不稳定性。
  2. 隔离优化贡献。同模型、同强度、同输入与输出要求，交错比较串行旧链／单次调用、冷／热缓存、启动预热、HTTP／WebSocket、标准／可用加速档位。记录缓存是否真正命中，不用时间顺序猜测。
  3. 验证自然表达。对同一事实与任务对比固定模板和单次自然生成；连续 20 轮以上观察重复和偏好执行。与只追求语气变化的版本对比，盲评并收集玩家打扰反馈。
  4. 验证图调度与竞争。新用户消息、状态骤变、结果乱序、断线重连、429、工具超时、记忆冲突、模型截断、缓存过期、发送时状态改变。测试集里任何过时动作建议、跨 Agent 私有上下文泄漏或忽略明确停止都阻止该版本通过。
  5. 小流量学习。完成前面验收后再增加后台 Skill 优化与主动试探。每次只改少数变量，有版本、有保留集、有回滚；用真实用户结果判断，不只依靠模型自评。

测试样本通过不等于线上零故障。速度门槛、自然度与事实正确性一起报告；超时、取消、无有效回答的请求必须保留数量和失败率，不能只从成功请求里挑最快样本。若同模型配置达不到延迟目标，下一步才比较更快模型或更多可验证的本地技能，不把首句换成空话来达标。

十四、依据与实现边界

设计判断、初始预算、冷却、并发和验收门槛均为本方案建议。当前只交付可评审设计和示例，不宣称引擎已实现或再次完成模型测试。游戏知识、字段能力与更新频率必须以实际目标服务器接口为准。

  • OpenAI：流式响应——增量交付机制。
